Prepare and open concise draft pull request(s) for the current branch. Extra context: ${@:-none}

Load and follow the `git-worktree-stack` skill before inspecting branches or running Git workflow commands.

Invoking `/pr` authorizes this full workflow without intermediate approval, synchronization performed by `gwsync`, and new commits containing only accepted review fixes and behavior-preserving simplifications. Existing branch commits are valid; preserve them. No unrelated commit is allowed.

1. Preflight. Determine current and default branches. Stop if this is not a Git worktree, no `origin` exists, `gh auth status` fails, current branch is the default branch, working tree is dirty, or an open PR already exists for the current branch. Never stash or discard work.
2. Parent and sync. Resolve the immediate parent using the `git-worktree-stack` skill. If none is recorded, inspect branch ancestry and remote PR/stack metadata; use the default branch only when the branch is clearly direct, and ask if the parent remains ambiguous. Record the confirmed parent through the workflow's shared lineage mechanism before syncing. Run `gwsync --no-push` through zsh as documented by the skill, then resolve the parent again. Stop on conflicts, skipped branches, or any sync failure. Parent equal to default means direct PR; any other parent means stacked PR. Use only `git diff <parent>...<branch>` for that branch's scope and stop if it is empty.
3. Choose PR shape. Inspect the parent-relative diff, changed files, and existing commits. Keep one PR when the change is cohesive and reviewable; multiple commits alone are fine. Preserve an existing stack. If a direct change is too large, touches too many files to review clearly, or contains independently reviewable dependency layers, use `gwa` and the shared lineage mechanism to split it into the smallest dependency-ordered stack. Preserve commits when possible; ask before rewriting published history.
4. Review and fix every final layer. After branch shape and parents are final, run `gwsync --no-push` from the top branch. Before any push or PR creation, run a parent-controlled review loop for each PR branch against only `git diff <immediate-parent>...<branch>`. In each round, have the parent write that exact diff to a temporary artifact outside the repository, then use one async `workflowScript` with stable keys and `runs.all(...)` to launch two fresh-context `reviewer` tasks: one with `skill: "code-review-and-quality"` for the five-axis review and validation gaps; one with `skill: "code-simplification, ponytail-review"` to find unnecessary complexity and propose the smallest behavior-preserving fixes. Use these skills as review guidance only: this prompt controls scope, severity, and what can be changed or published. Give both read-only reviewers the artifact's absolute path and matching repository/worktree path; require them to read the artifact and referenced files rather than run Git commands or edit code, including for mutation tests. Have them use P0/P1/P2 severity based on impact, not the skills' labels. Await the ordered results and synthesize them in the parent. When supported P0/P1 fixes or clear behavior-preserving simplifications remain, have one `worker` apply only those accepted findings on the branch where they belong, run the smallest relevant existing checks, stage only review changes, and commit them directly with a concise message. Run `gwsync --no-push` from the top branch so descendants include parent fixes, then repeat with fresh reviewers. Stop when reviewers report no P0/P1 findings and no clear simplifications, or after three rounds; stop without pushing if actionable findings remain. Do not loop on optional P2 polish or parse reviewer prose as a workflow verdict.
5. Test each final layer before pushing. Start with the smallest relevant project tests, including repeatable UI tests through the project's test runner even when they use a browser or emulator. Unless separately requested, drive a browser or device directly (for example, with Playwright or ADB) only in this step, using the project's documented setup when needed to verify changed behavior or capture relevant screenshots. Keep screenshots outside the repository and check that they contain no secrets or private data before attaching them. Report skipped checks and missing screenshots with reasons.
6. Describe only each layer. For each PR, first inspect its branch name for a Linear issue key case-insensitively (for example, `xxx/oltf-597-feature-name` → `OLTF-597`). If a key exists, search for that exact issue through available Linear MCP tools before drafting the title or body; read the matching issue for motivation and use its URL in the body when found. Never configure MCP from this workflow. If Linear MCP is unavailable or the issue is not found, report that limitation and continue using the branch key without inventing issue details. Derive the change description only from `git diff <immediate-parent>...<branch>`; never describe inherited parent changes or claim unimplemented issue requirements. Always use a conventional-commit-style title with a lowercase type chosen from `feat`, `fix`, or `chore` to match the diff: `<type> [<LINEAR-KEY>]: Short Description` when the branch contains a key, otherwise `<type>: Short Description`. Normalize the key to uppercase; for example, `feat [OLTF-597]: Add deposit guidance` or `fix: Handle missing account`. Read `.github/pull_request_template.md` when present and fill it minimally. Without a template, use only a short `## Why` section.
7. Create draft PRs. For a direct branch, push normally and run `gh pr create --draft --base <parent> --title <title> --body <body>` with the title and body from step 6. For a stack, run `gwsync --link` from the top branch as documented by `git-worktree-stack`, verify every expected PR exists and remains draft, then update each new PR title and body with `gh pr edit` using its title and parent-relative description from step 6. For GitHub PRs, always upload local screenshots with `--attach '<file>#<descriptive alt text>'` on `gh pr create` for direct PRs or `gh pr edit` for stacked PRs. Repeat the flag for each image and attach it only to the PR it verifies. If an attachment fails, report the error and any PR URL already created; do not use another upload method.

Never run a manual force-push, merge, squash, delete branches, or modify unrelated PRs. Managed `--force-with-lease` inside `gwsync` or `gh-stack` is allowed. Stop on command failure and report exact error and every PR URL created.
